# TradingView Webhook 活动流设计

## 目标

让信号中心同时回答两个不同问题：

1. TradingView Alert 是否仍能把 Webhook 送达系统；
2. TradingView 是否真正发出了开仓或退出信号，以及后端如何处理该信号。

页面不得把链路心跳表述成开仓信号，也不得因为展示心跳而改变任何交易行为。

## 产品口径

- `STATUS` 是蓝色的“链路心跳”。它只证明 TradingView、Alert、Webhook URL 和 passphrase 验证链路可用，不会入队开仓。
- `OPEN_REQUEST` 是绿色的“TradingView 开仓信号”。只要通过 Webhook 验证并收到该事件，事件类型就标绿，表示 TradingView 的开仓条件已成立。
- 后端执行结果与事件颜色分开展示：
  - 黄色徽标：处理中；
  - 绿色徽标：系统已接受；
  - 红色徽标：系统拒绝。
- 被拒绝的 `OPEN_REQUEST` 仍保持绿色事件类型，同时显示红色“系统拒绝”徽标。用户点击记录后可查看拒绝原因。
- `EXIT_DVOL` 等退出信号使用紫色事件类型，仍显示独立的后端处理结果。

## 数据设计

### 心跳历史

新增独立的 `pine_heartbeats` 表，不把 `STATUS` 写入 `signals` 表。每条记录保存：

- 接收时间 `received_at`；
- Pine 对应的 2 小时 K 线时间 `bar_ts`；
- strategy、BTC 价格、OHLC、CCI、HV 分位、布林轨、DVOL 参考数据与各条布尔判定；
- 不保存 passphrase。

只有通过 passphrase 验证且 payload 可正常解析的 `STATUS` 才进入心跳历史。无效口令和非法 payload 不出现在正常活动流中。

每次写入后只保留最新 500 条心跳，避免长期运行无限增长。现有 `system_state.pine_status` 仍继续保存最新心跳，供开仓条件看板和推送看门狗使用。

### 统一活动流 API

`GET /api/signals` 扩展为返回按接收时间倒序合并的活动流：

- `kind=HEARTBEAT`：来自 `pine_heartbeats`；
- `kind=OPEN_SIGNAL` / `EXIT_SIGNAL`：来自现有 `signals`。

同时返回分开的摘要计数：心跳数、开仓信号数、退出信号数，以及开仓/退出信号的处理中、接受、拒绝数。心跳不纳入交易信号的接受率和拒绝率。

API 默认返回最新 100 条，保留现有 `limit` 上限 500。

## 前端设计

现有“TradingView 实时监听”区域改为统一时间流，不新增独立页面。

### 行样式

- 心跳：蓝色图标/左边线，标题“链路心跳”，副文案“TradingView 已连接 · 不触发开仓”。
- 开仓信号：绿色图标/左边线，标题显示 PUT/CALL 信用价差。
- 退出信号：紫色图标/左边线。
- 开仓和退出记录的右侧显示独立处理结果徽标，心跳显示“链路正常”徽标。

### 展开详情

每条记录可点击展开，且一次只展开一条：

- 心跳详情：接收时间、2h bar 时间、BTC 价格、HV/CCI/DVOL 值和逐项结论、Put/Call 形态。
- 信号详情：signal_id、接收时间、TradingView 参数、后端状态。
- 拒绝详情：优先显示可读的中文原因，并保留原始拒绝代码供排查。

拒绝代码的中文映射至少覆盖：交易开关关闭/强平锁定、已有期权卖方仓位、DVOL 低于开仓门槛、无有效期权腿、风险预算不足、payload 非法与重复信号。

## 交易安全边界

- 心跳历史的写入与展示不调用 `queue.open()`，不创建父交易，不修改 trading flag。
- 开仓权威链路保持不变：只有经验证的 `OPEN_REQUEST` 可入开仓队列，并继续接受现有仓位、DVOL、风险预算与交易开关检查。
- 前端只读，展开记录不发送控制请求。
- API 和前端不返回、不记录、不渲染 passphrase。

## 错误与降级

- 心跳历史写入失败时，Webhook 必须返回可观测的错误，但不得将未持久化的心跳表述为成功。最新 `system_state.pine_status` 与历史写入在同一数据库事务中完成。
- 活动流 API 查询中的单条损坏 payload 降级为空详情，不阻断整个列表。
- 无历史数据时显示“尚未收到 TradingView 心跳或信号”，不伪造演示数据。

## 测试与验收

### 后端

- 通过验证的 `STATUS` 同时更新最新心跳并追加历史，且不产生开仓命令。
- 无效 passphrase 的 `STATUS` 不写入最新心跳和历史。
- 心跳保留上限为 500，超出时删除最旧记录。
- 统一 API 按时间倒序合并心跳和交易信号，摘要计数不混淆心跳与交易信号。
- 被拒绝的 `OPEN_REQUEST` 仍返回 `kind=OPEN_SIGNAL`，同时返回拒绝状态和原囋原因代码。

### 前端

- 心跳行为蓝色且含“不触发开仓”文案。
- 所有 `OPEN_REQUEST` 事件为绿色，被拒绝时同时显示红色结果徽标。
- 点击心跳、已接受信号和已拒绝信号均可展开，再次点击可收起。
- 拒绝详情显示中文原因和原始代码。
- 桌面和宽度不超过 700px 的移动布局均可读。

### 回归与部署

- 全部 Python 测试、前端 Node 测试、Vite 生产构建和启动集成测试通过。
- 使用现有 testnet 云端打包/安装流程更新 `43.160.202.151`。
- 部署后验证 systemd 服务、公网 HTTPS、统一活动流 API，并确认数据库历史保留、testnet 环境和交易开关状态未被意外改变。

## 非目标

- 不改变 Pine 开仓条件、信号频率或交易参数。
- 不从前端人工生成开仓信号或心跳。
- 不为无效口令的请求提供可见的正常记录。
- 不将“TradingView 发出开仓信号”等同于“后端已成交开仓”。
